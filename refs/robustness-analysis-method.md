# ロバストネス分析手法ガイド

ロバストネス分析は、ユースケース（要求）を論理的な設計要素に変換するための手法です。

## 1. 相互作用の 4 つの基本ルール
図を記述する際は、以下の接続ルールを厳守してください。これに反する図は「不整合」と見なされます。

1.  **アクターは境界（Boundary）としか話せない**: ユーザーが直接ロジック（Control）を叩いたり、データ（Entity）を覗くことはできない。
2.  **境界（Boundary）は制御（Control）としか話せない**: 画面が直接データを保存・読み込みしてはいけない。必ずロジックを通す。
3.  **制御（Control）は、境界、他の制御、エンティティと話せる**: ロジックは UI に結果を返し、他のロジックを呼び出し、データを読み書きできる。
4.  **エンティティ（Entity）は制御（Control）としか話せない**: データ自身が画面に表示されたり、他のデータに干渉することはない。

## 2. ID 体系へのマッピング
ロバストネス図の要素は、設計ドキュメント（REQ-XXX.md）の以下の ID に対応させます。

| 図の要素 | ID 種別 | 設計上の役割 |
| :--- | :--- | :--- |
| **境界 (Boundary)** | **SPEC-XXX-YYY** | UI の振る舞い、入力・表示の要件。 |
| **制御 (Control)** | **FUNC-XXX-YYY-ZZZ** | 最小単位のビジネスロジック、機能。 |
| **エンティティ (Entity)** | **DATA-XXX-ZZZ** | 論理データ構造、永続化対象。 |

## 3. 分析の進め方
1.  **アクターの特定**: 誰が（何が）トリガーを引くか。
2.  **境界の特定**: ユーザーが目にする画面や入力を受ける口。
3.  **主要ロジックの抽出**: 入力を受けて「何をするか（Control）」。
4.  **データの特定**: そのロジックが「何を読み書きするか（Entity）」。
5.  **詳細化**: 抽出した Control を `FUNC` テーブルへ、Entity を `DATA` テーブルへ転記し、詳細（Input/Output等）を定義する。
